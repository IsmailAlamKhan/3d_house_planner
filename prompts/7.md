# Prompt 7 — AI Assistant: Prompt-to-Model and Prompt-to-Edit

## Goal
Let users describe what they want in plain language, such as *"3-bedroom duplex, open kitchen and living downstairs, master bedroom with attached bath upstairs"*, and get an editable model. Then let them refine it with commands like *"make the kitchen 1 meter wider"*.

## Architecture (`src/ai/`)
1. **Provider abstraction:** `interface LLMProvider { generate(req): Promise<string> }`. The app must work 100% free, so the defaults are local:
   - **Local Ollama (DEFAULT):** the browser never calls Ollama directly. It calls the app's own server endpoint `POST /api/ai`, which forwards to Ollama at `http://127.0.0.1:11434` (the proxy is built in prompt 13; until then, Vite's `server.proxy` points `/api/ai` at Ollama for development). Use Ollama's native `/api/chat` with `stream: false`, pass the DesignIntent / EditOperation **JSON Schema** (generated from the Zod schemas with `zod-to-json-schema`) in the `format` field so output is constrained to the schema, use `temperature` 0.2 and `num_ctx` 8192, and set `think: false` for models that support thinking. The model name is configurable, defaulting to `qwen3:14b`.
   - **OpenAI-compatible (optional):** a configurable base URL, for LM Studio (`http://127.0.0.1:1234/v1`) or llama.cpp server. Also routed through `/api/ai`.
   - **Offline generator:** a rule-based fallback that needs no model at all (see step 5). It is used automatically when the local model is unreachable, with a small banner saying so.
   - Settings screen: provider, model name, a "Test connection" button that lists models installed in Ollama (via `/api/tags` through the proxy), and a clear status indicator.
   - Don't add any paid or cloud provider by default.
2. **Two modes**
   - **Generate:** the input is a brief plus shell constraints, and the output is a `DesignIntent`.
   - **Edit:** the input is the current project summary, the selection, and a command. The output is a list of `EditOperation`s.
3. **Intermediate format, not raw geometry.** The LLM never outputs wall coordinates directly. It outputs a validated **DesignIntent** (Zod), for example: levels, then rooms per level with `type, name, targetArea, minWidth, adjacency (rooms it must connect to or open into), exteriorWall preference, needsWindow, needsPlumbing`, plus stair type and position preference, plus style or material hints.
4. **Layout solver** (`src/ai/layout/`), deterministic TypeScript code that turns a DesignIntent into a real model:
   - Place the stair first, aligned between levels. Place wet rooms (kitchen, bathrooms) near the shell's fixed plumbing points, and stack upstairs bathrooms above downstairs ones where possible.
   - Use a squarified or slicing-tree subdivision of the shell footprint, weighted by target areas and respecting minimum widths. Run an adjacency-aware ordering pass, then check that every room is reachable through a door, adding corridor space if needed.
   - Generate walls (exterior along the footprint, interior partitions), doors between adjacent rooms per the adjacency rules, windows on exterior walls for rooms that need them, and basic default furniture per room type, with an option to turn this off.
   - Avoid locked columns: snap partitions so columns sit inside walls where possible.
   - Report unmet constraints back to the user in plain language.
5. **Offline generator:** parse simple briefs (bedroom and bathroom counts, room keywords, open-plan wording) into a DesignIntent using keyword rules plus a few duplex templates, so the feature works without a key.
6. **Edit operations:** a Zod union such as `resizeRoom, moveWall, addRoom, removeRoom, renameRoom, changeMaterial, addItem, removeItem, moveItem, addOpening, changeStairType`. Apply all operations from one command as a **single undo batch**. Before applying, show a preview diff in the panel: "Will change: Kitchen 12.0 → 15.2 m², move wall W12 by 1.0 m."
7. **Robustness**
   - Use schema-constrained output (Ollama `format` with a JSON Schema), plus a system prompt with the schema and 1–2 short examples, because small local models do much better with examples.
   - Keep prompts compact: send a short project summary (rooms, sizes, levels), never the full project JSON.
   - Strip code fences, then validate with Zod. On failure, send the validation errors back to the model once (one repair round-trip) before showing a friendly error.
   - Show a timeout and cancel button. Never apply a partial result.
8. **UI** (left sidebar, "AI Assistant" tab)
   - A chat-like input, example prompt chips, and an "Apply" or "Discard" choice for each result.
   - Generating offers "Generate 3 variations", shown as thumbnails to pick from.
   - Show which provider is active, with the offline generator labeled as such.

## Acceptance criteria
- With no API key, the offline generator turns "2 bedroom duplex with open kitchen" into a valid two-level model with stairs, doors, and windows.
- With Ollama running locally, generation and edits work, edits undo in one step, and invalid AI output never corrupts the project.
- With Ollama stopped, the app falls back to the offline generator with a clear message instead of failing.
- The layout solver and the edit-operation application have unit tests, including the case where adjacency can't be met.
